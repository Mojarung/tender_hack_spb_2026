# Как мы обходим защиту маркетплейсов

Шпаргалка для защиты. Текст можно читать вслух — формулировки подобраны так,
чтобы термины звучали естественно и не цеплялись в речи.

---

## Почему вообще нужно «обходить»

У Wildberries и Ozon стоит антибот — система, которая отличает живого
покупателя от скрипта. Если она решит, что трафик автоматизированный,
сайт либо вернёт ошибку 403, либо подсунет CAPTCHA, либо начнёт отдавать
пустые карточки. Для агрегатора цен это смерть: одна капча — и весь поток
данных останавливается.

Антибот смотрит на три вещи:

1. **Сетевой отпечаток.** Когда программа на Python делает HTTPS-запрос,
   у её соединения свой характерный «почерк» — TLS-хендшейк, набор
   шифров, порядок расширений. Этот почерк называется **JA3-fingerprint**.
   У реального Chrome он один, у `requests` или `httpx` — другой, и
   маркетплейс это видит сразу.
2. **HTTP-заголовки.** Реальный браузер шлёт десятки заголовков:
   `User-Agent`, `Accept-Language`, `Sec-Fetch-Site`, `Sec-Ch-Ua`,
   `Referer`. Скрипт, который шлёт только `User-Agent`, виден насквозь.
3. **Cookies и поведенческие признаки.** При первом заходе на сайт
   Chrome выполняет JavaScript-челлендж, получает специальные cookies
   (например, `__Secure-ext_xcid` у Ozon) и только потом получает доступ
   к API. Скрипт без браузера эти cookies получить не может.

## Наша архитектура — каскад из трёх уровней

Мы построили систему так, чтобы для каждого источника использовать
**минимально достаточный уровень защиты** — лёгкий путь работает в 95 %
случаев, тяжёлый запускается только когда лёгкий упёрся в блокировку.

### Уровень L0 — rate limiter

Самый простой слой: ограничение скорости запросов. Мы не дёргаем источник
чаще, чем `rpm` (requests per minute) из конфига — для Wildberries это
6 RPM, для Ozon 20 RPM. Так мы не провоцируем антибот вообще.

Реализовано через **token bucket** в Redis: каждый поток нашего бэкенда
берёт «токен» из общего бюджета, и если токенов нет — ждёт. Без этого
несколько параллельных запросов могли бы пробить лимит и устроить
коллективный 429.

### Уровень L1 — curl_cffi с TLS-импертонизацией

Если просто послать запрос — поймаем JA3-блок. Поэтому мы используем
библиотеку **`curl_cffi`** — это обёртка над `libcurl-impersonate`,
которая умеет имитировать TLS-почерк реального Chrome байт-в-байт.

В коде это выглядит как `curl_cffi.AsyncSession(impersonate="chrome")`.
На стороне сервера Ozon такое соединение неотличимо от настоящего
Chrome — JA3 совпадает, набор cipher suites совпадает.

К этому мы добавляем правильный набор HTTP-заголовков (`Sec-Fetch-*`,
`x-o3-app-name`, корректный `Referer`), берём warmed-up cookies из
браузерного кэша и стучимся напрямую в внутренний API маркетплейса.

Для Wildberries L1 — это публичный JSON-API `search.wb.ru` (он
работает без аутентификации, но мы всё равно подмешиваем chrome-почерк).
Для Ozon L1 — это `composer-api.bx`, бэкенд их витрины.

### Уровень L2 — настоящий браузер с stealth-инъекциями

Когда L1 не пробивает (Ozon рандомно может потребовать JS-проверку),
мы поднимаем настоящий Chrome через библиотеку **`nodriver`**. Это
форк undetected-chromedriver — Chrome без сигнатур автоматизации.

Стандартный Chrome, запущенный программно, выдаёт себя через десяток
JavaScript-признаков: `navigator.webdriver === true`, отсутствие
плагинов, странный WebGL vendor, отсутствие звуковых устройств. Любая
страница может это прочитать.

Мы делаем **stealth-инъекцию**: до того, как любой скрипт страницы
успеет выполниться, мы через CDP (Chrome DevTools Protocol) делаем
`Page.addScriptToEvaluateOnNewDocument` и подменяем все эти признаки:

  • `navigator.webdriver` ставим в `undefined`;
  • `navigator.languages` ставим в `["ru-RU", "ru"]`;
  • `navigator.hardwareConcurrency` фиксируем на 8;
  • `navigator.deviceMemory` ставим в 8;
  • WebGL vendor/renderer подменяем на реальные строки от NVIDIA;
  • Canvas-fingerprint размываем шумом в младших битах (LSB-noise);
  • Notification.permission приводим к ожидаемому состоянию.

После этого браузер с точки зрения сайта неотличим от обычного.

## Конкретно для Ozon

У Ozon самая жёсткая защита, поэтому здесь у нас полный пайплайн.

1. **Warm-up cookies**. При старте бэкенда мы один раз поднимаем headed
   Chrome через `nodriver`, заходим на `ozon.ru`, потом на страницу
   поиска, ждём 3–5 секунд пока выполнятся JS-челленджи. Из браузера
   экспортируем 14–15 cookies и сохраняем на диск (`var/profiles/ozon`).
2. **Кэш на 12 часов**. Эти cookies валидны 12 часов — всё это время
   все запросы к Ozon идут через `curl_cffi` с готовым набором cookies,
   быстро и дёшево.
3. **L1-запрос** — POST в `composer-api.bx/page/json/v2` с правильным
   `dweb_client` headers и chrome-impersonation.
4. **Fallback на entrypoint-api** — если composer вдруг отдал 403,
   пробуем альтернативный хост `entrypoint-api.bx`.
5. **L2 fallback** — если HTTP-путь окончательно сломался, открываем
   таб в браузере, навигируем на страницу поиска и через
   `same-origin fetch` дёргаем тот же composer-api прямо из контекста
   страницы. С точки зрения Ozon это **обычный пользовательский AJAX**,
   против которого антибот бессилен.
6. **Auto-recovery**. Если пользователь случайно закрыл окно браузера,
   мы ловим `ConnectionClosedError`, сбрасываем синглтон браузера, и
   следующий запрос поднимает Chrome заново.

Параллельно для каждой найденной карточки делаем три fetch-а
параллельно через семафор: PDP (карточка товара), characteristicsList
(характеристики) и reviewshelfpaginator (отзывы с фото).

## Конкретно для Wildberries

У WB защита мягче — есть открытый JSON API.

1. **search.wb.ru/exactmatch/ru/common/v18/search** — без авторизации,
   но с лимитом ~10 RPS на IP. На 429 ставим cooldown 120 секунд, чтобы
   не долбить и не углубить бан.
2. **Региональность** — добавляем параметр `dest=-1257786` (это код
   московского склада в системе WB).
3. **Характеристики и отзывы** — для каждой найденной карточки
   параллельно через нашу WB-обёртку браузера тянем
   `basket-{NN}.wbbasket.ru/.../card.json` и
   `feedbacks.wb.ru/feedbacks/v1/{imt_id}`.

Здесь тоже есть отдельный стелс-браузер (свой персистентный профиль в
`var/profiles/wb`, изолированный от Ozon), но используется он только
тогда, когда нужно достать данные, которых нет в публичном API.

## Четвёртый источник — Рунет

WB и Ozon — это два маркетплейса. По правилам хакатона нужен ещё
«плавающий» четвёртый источник из открытого Рунета. У нас это
**SearXNG + Яндекс/Google Shopping**:

  • поднимаем self-hosted SearXNG локально (это метапоисковик —
    свой, без внешних API, как требует регламент);
  • дёргаем органическую выдачу Яндекса по запросу;
  • из топ-N не-маркетплейсовых URL парсим JSON-LD Product (это
    стандартный schema.org разметка), оттуда вытаскиваем цену,
    название, рейтинг;
  • плюс параллельно открываем Google Shopping в стелс-браузере и
    забираем оттуда первые 5 карточек с их характеристиками.

Эти два потока (Яндекс + Google) сливаются в один источник «Рунет»
с дедупликацией по продавцу.

## Что мы НЕ делаем (и почему)

  • Не используем платные прокси или внешние scraping-API (Firecrawl,
    Scrapfly, ZenRows, Bright Data). По регламенту хакатона
    (методичка, стр. 5) внешние API запрещены — только своё.
  • Не решаем капчи через антикапча-сервисы. Если упёрлись в капчу —
    значит, что-то в каскаде сломалось, и нужно чинить, а не платить
    стороннему сервису.
  • Не делаем DDoS. Все лимиты выставлены ниже разумных — мы
    создаём нагрузку как один активный пользователь, не больше.

## Главное за 30 секунд

«У маркетплейсов стоит антибот, который ловит скрипты по трём
признакам: сетевому почерку, заголовкам и cookies. Мы построили
трёхуровневый каскад: rate-limiter, потом curl_cffi с chrome-импертонизацией,
потом настоящий браузер со stealth-инъекциями. Лёгкий путь работает в
95% случаев, тяжёлый запускается только когда лёгкий упёрся. Для Ozon
дополнительно греем cookies через headed Chrome раз в 12 часов. Никаких
внешних API не используем — всё self-hosted, по регламенту хакатона.»
